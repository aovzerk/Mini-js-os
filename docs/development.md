# Разработка и проверка

## Требования

- Windows PowerShell;
- Open Watcom в `C:\WATCOM` и его инструменты в PATH;
- FASM;
- QEMU `qemu-system-i386`.

Сборка:

```powershell
.\build32.ps1
```

Сборка и интерактивный запуск:

```powershell
.\run32.ps1
```

Готовый образ: `build32\myos32.img`.

## Программы в образе

- `SHELL.BIN` — командный shell;
- `PRINT.BIN` — печать аргумента;
- `GUI.BIN` — рабочий стол и оконный менеджер;
- `EDITOR.BIN` — графический редактор `.TXT`;
- `LS.BIN` — список файлов;
- `CAT.BIN` — вывод содержимого файла;
- `JS.BIN` — интерпретатор файлов с небольшим подмножеством JavaScript;
- `JSGUI.BIN` — тот же JS-runtime с `AppType = 1` для GUI-скриптов;
- `POWEROFF.BIN` — выключение;
- `NOTES.TXT` — заранее выделенный текстовый файл;
- `JSTEST.JS` — проверочный скрипт для управляющих конструкций, объектов,
  функций, таймеров, их отмены, `console.log` и комментариев;
- `APITEST.JS` — проверка встроенного модуля системного API `myos`;
- `MONITOR.JS` — автообновляемое дерево процессов с PID родителя и
  терминального канала; кадр формируется самим JS-скриптом атомарно;
- `SHELLICO.PNG` — PNG-иконка терминала.

Исходные JS-программы, добавляемые в системный образ, хранятся в
`pm32/js_scripts`. Точка сборки интерпретатора — `pm32/user/js/js.c`, точка
сборки ядра — `pm32/kernel/core/core.c`, оконного сервера —
`pm32/user/gui/gui.c`. Остальные файлы в этих каталогах являются логическими
модулями одной translation unit.

Новый исходный файл желательно удерживать в пределах 200 строк. При росте
модуль разделяется по ответственности. Допустимое исключение — одна неделимая
функция, если её разбиение потребует искусственного общего состояния; сейчас
таким исключением является `kernel_dispatch` в `core/dispatch.c`.

## Добавление программы

Шаблоны и объяснение ABI приведены отдельно в
[c-applications.md](c-applications.md) и
[js-applications.md](js-applications.md).

1. Создать `pm32/user/name.c`.
2. Поставить `_start` первой функцией в бинарном образе.
3. Добавить имя в массив `$programNames` файла `build32.ps1`.
4. Добавить FAT entry в массив `$files`, указав `AppType`.
5. Собрать и проверить размер `.BIN`.

Общие строковые функции нужно добавлять в `pm32/lib/userlib.c` и
`pm32/include/myos/userlib.h`, общие ABI-типы — в
`pm32/include/myos/types.h`, а GUI-вызовы — в `pm32/include/myos/gui.h`.
Не копировать одинаковые
`write_text`, `FileRequest` и syscall pragma в каждую программу.

GUI-программа после старта должна вызвать `sys_gui_create_window()`. Окно
создаёт GUI-сервер после получения IPC-запроса; приложение не должно напрямую
добавлять себя в массив окон GUI-сервера напрямую.

Имя файла в FAT должно быть ровно 11 символов: восемь для имени и три для
расширения, например `LS      BIN` или `POWEROFFBIN`.

## Обязательная проверка

После изменений ядра или загрузчика запускать QEMU с:

```text
-no-reboot -d int,cpu_reset,guest_errors
```

В журнале не должно быть `check_exception` или `Triple fault`. Простого факта
сборки недостаточно: ошибки адресации проявляются только при выполнении.

После изменения FAT32-записи дополнительно проверить root directory и содержимое
созданного файла непосредственно в `myos32.img` после завершения QEMU.

## Критичные ограничения

- IDT и полноценные обработчики исключений пока отсутствуют. Любой #GP/#PF/#UD
  переходит в double/triple fault, что выглядит как перезапуск QEMU.
- Планировщик кооперативный, аппаратного вытеснения и обработчика прерываний
  таймера нет. Монотонные часы считываются из PIT по запросу.
- FAT32 поддерживает только root и contiguous files.
- Максимум 16 root entries просматривается ядром.
- Максимальный редактируемый файл — 4096 байт.
- JS-интерпретатор работает с целыми 32-битными числами, динамическими строками,
  простыми объектами, пользовательскими/стрелочными функциями и
  кооперативными таймерами. Один оператор по-прежнему должен находиться на
  одной строке; массивы, вложенные объекты и стандартный JavaScript API пока
  не реализованы.
- Пользовательский heap занимает 64 КБ. `sys_malloc` выдаёт обнулённые блоки,
  `sys_free` обнуляет и объединяет освобождённые блоки.
- Плоский JS-runtime вместе с данными должен заканчиваться раньше `0x2E000`, где
  ядро размещает строку аргументов. Слишком большие статические таблицы могут
  быть повреждены при старте программы.
- Терминальный канал ядра — 256 байт; большой вывод отправлять частями.
- Физическая консоль хранит 64 строки истории; `Page Up`/`Page Down` листают
  старый вывод.
- Пользовательские программы имеют IOPL3, потому что GUI пока напрямую работает
  с VGA/PS2. Это учебное упрощение, а не безопасная архитектура.
- GUI сейчас поддерживает максимум три окна.

## Диагностика типичных проблем

- Перезапуск сразу после boot: проверить GDT base, физические адреса загрузки и
  линковки C-ядра.
- Fault с EIP около `0x00000003`: вероятно, `_start` не первая функция плоского
  пользовательского файла.
- Пустой вывод дочерней программы: проверить `terminal_pid`, PID окна и лимит
  терминального канала. Канал `0` означает физическую VGA-консоль; GUI-сервер
  выдаёт каждому терминальному окну ненулевой канал.
- Файл не найден: проверить точное имя FAT 8.3 и наличие записи в `$files`.
- Файл не сохранился: проверить ATA status, обе FAT и root sector.
