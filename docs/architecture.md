# Архитектура MyOS

## Общая схема

MyOS — учебная 32-битная ОС для x86. Загрузчик начинает работу в real mode,
загружает минимальную ASM-часть и C-ядро, после чего `entry.asm` включает
protected mode, paging и запускает пользовательский `SHELL.BIN` в CPL3.

Основные компоненты:

- `pm32/boot/boot.asm` — 512-байтный FAT32 boot sector и BIOS-загрузка;
- `pm32/kernel/entry.asm` — переход в protected mode и первый запуск CPL3;
- `pm32/kernel/syscalls.asm` — мост `int 80h`/`IRETD`, IRQ0/IRQ1/IRQ12;
- `pm32/kernel/x86_tables.asm` — GDT и TSS;
- `pm32/kernel/core/core.c` — точка сборки и общее состояние ядра;
- `pm32/kernel/core/*.c` — dispatcher, консоль, FAT32/ATA и процессы;
- `pm32/include/myos/api.h` — пользовательский syscall ABI;
- `pm32/include/myos/gui.h` — IPC API графических приложений;
- `pm32/include/myos/types.h` — общие типы и структуры ABI;
- `pm32/include/myos/userlib.h` — публичный API общей библиотеки;
- `pm32/lib/userlib.c` — реализация общей пользовательской библиотеки;
- `pm32/user/*.c` — небольшие плоские пользовательские программы;
- `pm32/user/gui/gui.c` и `pm32/user/gui/*.c` — оконный сервер и его модули;
- `pm32/user/js/js.c` и `pm32/user/js/*.c` — JS-runtime и его модули.

Сборочные точки расположены рядом со своими модулями и подключают их в одну
translation unit. Это сохраняет единый freestanding-образ и гарантированный
первый код `_start` пользовательских BIN без усложнения линковки Open Watcom.

Ядро разделено на `dispatch`, `console`, `filesystem`, чтение/запись файлов и
управление процессами. GUI разделён на video, terminal, desktop, taskbar,
keyboard и event loop. JS-runtime разделён на expressions, statements,
control flow, API calls, value I/O, source lexer и runtime startup.

## Загрузка

Образ имеет FAT32-разметку: 64 зарезервированных сектора, две FAT по 1009
секторов, затем корневой каталог и непрерывные данные файлов.

Boot sector выполняет два отдельных чтения системной области:

1. первые 16 секторов с ASM-entry загружаются по физическому адресу `0x8000`;
2. C-ядро, начинающееся с файлового смещения `0x2000`, загружается по `0x10000`.

Это разделение обязательно. Open Watcom принимает linker offset только на
границе 64 КБ, поэтому C-ядро линкуется непосредственно для `0x10000`.
Нельзя возвращать старую схему поиска и замены похожих на адреса четырёх байт
в готовом машинном коде: она повреждала инструкции и вызывала triple fault.

После загрузки `entry.asm`:

1. устанавливает GDT;
2. включает PE в CR0;
3. настраивает TSS и IDT для переходов CPL3 → CPL0;
4. вызывает C dispatcher для инициализации консоли и загрузки shell;
5. создаёт адресное пространство PID 0;
6. включает paging и переходит в CPL3 через `IRETD`.

## Карта памяти

| Адрес | Назначение |
|---:|---|
| `0x00008000` | ASM-entry, syscall bridge, GDT и TSS |
| `0x00010000` | C-ядро |
| `0x00020000` | виртуальная база пользовательской программы |
| `0x0002E000` | аргументы пользовательской программы |
| `0x0002F000` | начальный ESP пользовательского процесса |
| `0x00040000` | кеш корня FAT32 и непрерывных кластеров |
| `0x00080000` | массив page directory процессов |
| `0x00090000` | массив первых page table процессов |
| `0x00100000` | виртуальная база 128-КБ heap процесса |
| `0x00200000` | физические слоты процессов |

Размер одного физического пользовательского слота — `0x40000` (256 КБ).
Максимум процессов сейчас равен 8. Первая половина отображается в прежний
виртуальный image-диапазон `0x20000..0x3FFFF`, поэтому ABI программ сохранён.
Первые 124 КБ второй половины отображаются как `0x100000..0x11EFFF`, последние
4 КБ ядро резервирует под terminal snapshot процесса.

Диапазон `0x100000..0x11EFFF` используется как heap процесса. Ядро обслуживает
его через `sys_malloc`/`sys_free`, выдаёт выровненные и обнулённые блоки,
обнуляет освобождаемые блоки и полностью очищает heap при `spawn`, `exec`,
`exit` и принудительном завершении процесса.

## Формат пользовательских программ

Программа — плоский `.BIN`, слинкованный от `0x20000`. ОС всегда начинает
исполнение с первого байта файла, а не читает entry point из LX-заголовка.

Поэтому `_start` обязан быть первой сгенерированной функцией. Если перед ним в
C-файле находятся определения вспомогательных функций, процесс начнёт
исполнять неправильную функцию и после `return` обычно уйдёт на мусорный адрес.
Безопасный шаблон:

```c
#include <myos/api.h>

static void program_main(void);

void _start(void)
{
    program_main();
}

static void program_main(void)
{
    /* ... */
}
```

Тип программы хранится в байте 12 FAT directory entry:

- `APP_CONSOLE` (`0`) — консольная программа;
- `APP_GUI` (`1`) — программа, запускаемая только через GUI.

Ядро проверяет тип при `spawn`, `run` и `spawn_gui`.

## Процессы и терминалы

Планировщик вытесняющий: IRQ0 переключает активные процессы каждые 10 мс.
Контекст содержит EIP, ESP, EFLAGS, CR3 и все регистры общего назначения. GUI имеет PID 0 после замены shell
через `exec`; дочерние shell/editor получают отдельные PID.

В текстовом режиме PID 0 также используется для shell. Команды запускаются
через `sys_run` как дочерние процессы; shell ожидает ребёнка, сохраняя свой
EIP/ESP, а после `sys_exit` ребёнка планировщик возвращается прямо в сохранённый
код shell. Повторная загрузка `SHELL.BIN` с диска не выполняется. Завершение
самого PID 0 запрещено; после запуска GUI этот PID владеет рабочим столом.

Для каждого процесса существуют:

- очередь из 64 клавиш;
- терминальный канал ядра на 256 байт;
- родительский PID и PID терминального канала;
- имя текущей исполняемой программы длиной до восьми символов;
- заголовок GUI-окна длиной до 31 символа;
- флаги `active`, `started`, `waiting_child` и `app_type`.

Имя устанавливается при `spawn` и обновляется при успешном `exec`.
`sys_list_processes` возвращает массив структур `ProcessInfo` активных
процессов. Заголовок, ширину колонок и оформление таблицы формирует вызывающее
приложение.

GUI-приложение задаёт заголовок через `sys_gui_set_title`. GUI-сервер получает
его по PID через `sys_gui_get_title` и хранит собственную копию в записи окна.
Каждое видимое окно сразу получает кнопку на нижней панели. Кнопка активного
окна выделяется ярким цветом; нажатие на кнопку восстанавливает свёрнутое окно,
делает его активным и переводит на передний план.

`terminal_pid == 0` означает физическую текстовую консоль: вывод дочерней
команды идёт прямо в VGA, а клавиши читаются из PS/2. Когда GUI-сервер PID 0
создаёт shell, ребёнок получает собственный ненулевой канал; GUI читает его
через `sys_terminal_read`. `execute()` обязательно обновляет `app_type`, поэтому
после перехода `shell → gui` новые процессы маршрутизируются как GUI-дочерние.

Физическая VGA-консоль хранит scrollback на 64 строки. На экране отображаются
25 строк; при продолжении вывода окно автоматически следует за нижней частью
истории. `Page Up` и `Page Down` перемещают окно по старому выводу, а новый
вывод возвращает его к актуальной строке.

Ядро предоставляет монотонное время в миллисекундах, вычисляемое по счётчику
PIT. JS-runtime использует его для event loop; аппаратное вытеснение не зависит
от вызовов `sys_yield` внутри интерпретатора.

GUI хранит до 4096 символов на окно. Большой вывод отправляется порциями
меньше 256 байт; планировщик вытесняет производителя независимо от `sys_yield`.
Активное окно любого типа прокручивается клавишами `Up`/`Down` по одной строке
и `Page Up`/`Page Down` по десять строк.

Для периодически обновляемых окон терминальный протокол поддерживает пакетный
кадр. `beginUpdate()` очищает скрытое содержимое и запрещает промежуточный
`redraw`, `endUpdate()` публикует полностью сформированный кадр. Process Monitor
использует этот режим и выводит процессы деревом по `parentPid`, сохраняя
состояние, тип приложения и номер терминального канала.

Гибридный GUI использует C как native backend: он владеет VBE framebuffer,
backbuffer, PS/2 и шрифтом. GUI-процессы отправляют retained-команды рисования
через syscalls 28–29, а сервер доставляет им клавиатурные и мышиные события
через syscalls 30–31. Такой слой позволяет переносить desktop/taskbar policy в
JS, не выполняя попиксельный рендеринг внутри интерпретатора.
Фоновый retained-слой `desktop.js` уже рисует рабочий стол, три launcher-иконки
и основу taskbar. В C для этих элементов больше нет визуального fallback:
если JS-shell не представит кадр, композитор оставит эту область чёрной.
Overlay-слой предназначен для панелей и виджетов поверх окон.
Launcher-клики, кнопка питания и маршрутизация обычных клавиш активному PID
также выполняются `desktop.js`; C больше не запускает приложения по иконкам.
Native PS/2 backend отбрасывает стартовый шум и публикует button press только
после трёх пакетов подтверждённого release; JS получает готовые click-события.
ACK `0xFA` для команд настройки мыши вычитываются синхронно при инициализации и
не попадают в трёхбайтовый packet parser.
Предполагаемый press дополнительно подтверждается отдельным PS/2 status-запросом
`E9` при временно остановленном streaming; сырого button bit недостаточно.
Запуск приложений вынесен в `deskapps.js` и подключается пользовательским
`require("deskapps.js")`.
`windows.js` принимает window requests и задаёт рамку, task-кнопку и область
`drawTerminal`; постоянный 4-КБ terminal snapshot хранится в слоте процесса.
Процесс, созданный GUI-контроллером, получает собственный terminal channel,
чтобы JS window manager читал snapshot непосредственно по PID приложения.
`window.setTitle()` публикует заголовок через `sys_gui_set_title`, после чего
`windows.js` читает его через `getWindowTitle(pid)` и рисует в рамке и taskbar.

Графическое приложение само вызывает `sys_gui_create_window`. Ядро сохраняет
запрос в записи процесса, а GUI-сервер забирает его через
`sys_gui_next_window` и связывает новое окно с PID заявителя. Иконка редактора
только запускает процесс и больше не создаёт окно от его имени.

## FAT32 и запись

Ядро работает только с корневым каталогом и короткими именами FAT 8.3.
Длинные имена, вложенные каталоги и фрагментированные цепочки пока не
поддерживаются. `load_file` предполагает непрерывное размещение файла.

Запись выполняется ATA PIO через порты `0x1F0..0x1F7`. Обновляются данные,
обе копии FAT и root directory sector. Размер редактируемого файла ограничен
4096 байт. Новому пользовательскому файлу резервируется восемь кластеров из
области, начинающейся с кластера 400.

Редактор намеренно принимает только `.TXT`, чтобы не перезаписать системные
`.BIN` и PNG-файлы.

## Вытесняющее планирование

PIT работает с частотой 1000 Гц. Каждые 10 тиков IRQ0 сохраняет полный
контекст ring 3 (`EIP`, `ESP`, `EFLAGS`, `CR3` и регистры общего назначения)
и запускает round-robin планировщик. Поэтому процессу не требуется вызывать
`sys_yield`, чтобы другие процессы получили CPU.

`sys_yield` сохранён в ABI как добровольная оптимизация: процесс может сразу
отдать остаток своего кванта, когда ему нечего делать. Прерывание, пришедшее
во время выполнения ядра, только обновляет часы и не переключает контекст.
Ожидание JS-таймеров использует блокирующий `sys_wait_until`, поэтому runtime
не опрашивает `sys_millis` в плотном цикле и не расходует квант до deadline.

## Trap frames и системные вызовы

У каждого процесса есть отдельный supervisor-only trap frame, выбираемый по
его `CR3`. Вход `int 80h` больше не использует один общий mutable request для
всех процессов. IRQ0 имеет отдельный frame планировщика.

Диспетчер разделён по подсистемам: `syscall_input.c`, `syscall_time.c`,
`syscall_memory.c` и `syscall_gui_ipc.c`. `dispatch.c` остаётся только точкой
маршрутизации и обработчиком базовых process/filesystem вызовов. Поскольку
ядро пока собирается как flat binary с фиксированным C entry, `dispatch.c`
обязательно подключается первым.

PS/2-мышь инициализируется ядром до включения IRQ. Клавиатура обслуживается
IRQ1, мышь — IRQ12; оба обработчика записывают маркированные байты в bounded
ring buffer. GUI читает очередь через `sys_input_read` и не имеет кода прямого
доступа к портам PS/2.

Consumer-часть драйвера разделена в `kernel/core/input/`: `ps2.c` владеет
адресами и операциями ring buffer, `keyboard.c` преобразует scan-коды в
символы, `mouse.c` выдаёт только целые трёхбайтовые пакеты. Поэтому
`read_key()` не читает очередь мыши, а потеря пакета при переполнении не
нарушает синхронизацию следующих движений.
Накопившиеся mouse packets объединяются драйвером в одно результирующее
перемещение с последним состоянием кнопок. JS-курсор использует dirty-флаг:
ограничение частоты кадров откладывает кадр, но не может потерять последнюю
позицию.

IRQ12 за один вход ограниченно вычитывает все доступные AUX-байты PS/2
controller (`OBF=1`, `AUX=1`). Чтение только одного байта оставляло реальный
SDL/QEMU packet в output buffer, линия IRQ оставалась активной и после
небольшого движения курсор переставал получать новые фронты. Keyboard byte
обработчик мыши не забирает.

Курсор передаётся retained backend одной атомарной командой
`GUI_DRAW_CURSOR`, а не набором мелких `fillRect`. Команды обрабатываются
ограниченной порцией, несколько `PRESENT` объединяются, полный framebuffer
копируется не чаще одного программного кадра примерно за 33 мс.

Текстовая VGA-консоль реализована как kernel driver
`kernel/core/drivers/vga_console.c`: она отвечает только за видеопамять,
курсор и scrollback. Инициализация выполняется отдельным boot entry
`KERNEL_BOOT_INIT`, а не пользовательским syscall. Приглашение `> `,
командная строка и запуск программ полностью принадлежат `SHELL.BIN`.
